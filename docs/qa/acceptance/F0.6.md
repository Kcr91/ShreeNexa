# F0.6 Acceptance Contract — Dhan Rate Limiter with Redis Token Bucket

## Feature

Verify current Dhan REST limits, store dated limits in `config/dhan_limits.yaml`, and implement a distributed Redis token bucket rate limiter with jittered backoff in `backend/app/dhan/limiter.py`. Route all Dhan REST calls through it so that no request exceeds configured rate limits.

## Scope decisions recorded before implementation

- **Dated Limits Configuration**:
  - `config/dhan_limits.yaml` stores documented and verified rate limits per category, dated with `as_of` timestamp and provenance URL.
  - Categories include `default`, `option_chain` (1 req / 3.0s per spec §3.4), `historical_daily`, `historical_intraday`, `quotes`, `orders`, and `account_funds_holdings`.
  - Fallback mechanisms guarantee safe conservative limits even if the configuration file is missing or contains unknown categories.
- **Distributed Redis Token Bucket with Atomic Lua Execution**:
  - Token replenishment and consumption execute atomically in Valkey/Redis via Lua script (`redis.call('TIME')`).
  - Key namespace: `shreenexa:ratelimit:tokens:{category}` and `shreenexa:ratelimit:last:{category}` with TTL to prevent key accumulation.
  - Multi-process safe: multiple processes (`api`, `engine`, `feedd`, `worker`) sharing Redis respect the single global rate limit.
- **In-Memory Token Bucket Fallback**:
  - Thread-safe `InMemoryTokenBucket` implementation for unit tests or standalone execution when Redis is not available.
- **Jittered Backoff & Timeout**:
  - If a bucket is empty, the client calculates wait time with configurable randomized jitter to avoid thundering herds.
  - Requests waiting longer than `timeout` raise `DhanRateLimitError` (which has `is_retryable = True`).
- **Zero Bypassing Call Sites**:
  - All calls in `DhanRestClient` pass through `limiter.acquire(category)` before reaching the transport.
  - AST architecture tests assert that no un-rate-limited REST calls to Dhan exist in the codebase.

## Acceptance scenarios

### A1 — Dated configuration loading and category resolution
- Loading `config/dhan_limits.yaml` yields typed `DhanLimitsConfig`.
- Option chain requests map to category `option_chain` with 1 request per 3.0 seconds.
- Historical data requests map to `historical_daily` / `historical_intraday`.
- Missing or malformed configuration gracefully falls back to safe built-in defaults.

### A2 — Token bucket burst and refill mechanics
- A fresh bucket allows burst requests up to its `burst` capacity without delay.
- Once tokens are depleted, subsequent requests acquire tokens only as replenished by `rate` tokens per second.
- Token replenishment calculates accurately across fractional time intervals.

### A3 — Distributed Redis concurrency and invariant verification
- Multi-threaded concurrent workers requesting tokens from `RedisTokenBucket` never exceed $Capacity + Rate \times T$ requests within time window $T$.
- Tests against live Valkey/Redis container confirm atomic multi-worker synchronization.

### A4 — Jittered backoff and timeout handling
- When tokens are unavailable, `acquire()` sleeps for the calculated duration plus random jitter.
- If tokens cannot be acquired within `timeout` seconds, `DhanRateLimitError` is raised.

### A5 — DhanRestClient automatic rate limit enforcement
- `client.get_fund_limits()`, `client.get_historical_daily(...)`, and all other client methods automatically invoke `limiter.acquire()` with their respective category before sending requests.

### A6 — Zero bypassing call sites
- AST architecture inspection of `backend/app` confirms every Dhan HTTP interaction routes through the rate limiter.
