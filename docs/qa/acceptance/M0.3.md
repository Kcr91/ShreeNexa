# M0.3 Acceptance Contract — Data Lifecycle and Rollback

## Feature

Define ShreeNexa's data root, immutable raw-download policy, warehouse versioning, backup boundary, rollback behavior, and disk-capacity alarms before any warehouse implementation.

## Required deliverables

1. An accepted ADR defining the path boundary and lifecycle policy.
2. A data-lifecycle document with directory purposes, state transitions, ownership, retention class, and recovery behavior.
3. A versioned warehouse-manifest contract sufficient to identify exact backtest inputs.
4. An atomic publication and rollback procedure that never rewrites an existing warehouse version.
5. Warning, critical, and write-stop disk thresholds with explicit operator behavior.
6. A backup inclusion/exclusion matrix.
7. A project-status update after implementation and after review.

## Acceptance scenarios

### A1 — Path containment

- The default data root is inside this repository's ignored `data/` directory.
- An override must be an absolute, dedicated ShreeNexa path with an ownership marker.
- Drive roots, temporary directories, the repository source root, and the legacy project are rejected as override roots.
- All derived paths are resolved and verified as descendants of the selected root before any write.

### A2 — Immutable raw data

- A successful upstream response is stored byte-for-byte with a SHA-256 digest and a redacted metadata sidecar.
- Authentication headers, tokens, cookies, and credentials are never stored.
- Corrections or retries create new ingest artifacts; no raw payload is edited in place.
- Downstream versions identify every raw-ingest ID used.

### A3 — Warehouse publication and rollback

- Partitions are written and verified in staging before publication.
- A version manifest records schema, source ingest IDs, partition digests, row counts, ranges, provenance, code commit, and parent version.
- Publication changes an atomic current-version pointer only after all files validate.
- Rollback repoints to a prior complete version and does not mutate either version.
- A backtest can retain its original version and manifest digest after current moves forward or backward.

### A4 — Backup boundary

- Postgres dumps, raw artifacts, warehouse versions/manifests, reviewed configuration, and required provenance are included.
- Redis hot state, caches, staging files, temporary exports, logs, and secrets are excluded from the normal data backup.
- A backup destination is outside the primary data root and is not represented as complete until restore validation succeeds.

### A5 — Capacity safety

- Every filesystem used by primary data, database/container storage, temporary atomic writes, or backups is monitored.
- Thresholds are ordered warning > critical > write stop.
- A projected write that would cross the stop reserve is rejected before download or publication.
- Capacity failures never trigger automatic deletion of raw data or published warehouse versions.

## Verification

- Check every configured example path is ShreeNexa-owned and contains no legacy dependency.
- Check the lifecycle state machine has no transition that mutates a published version.
- Check each durable artifact appears in the backup matrix and each reconstructible artifact is explicitly classified.
- Check threshold ordering for both percentage and absolute reserves.
- Resolve local documentation links, scan for secret-shaped content, and run `git diff --check`.

## Non-goals

- No runtime `data/` directory or external data root is created.
- No market data is downloaded.
- No database, container, dependency, schema, migration, backup job, or monitoring process is installed.
- No retention deletion is automated.
- No production backup destination is selected; Epic 13 implements and restore-tests it.

## Migration and rollback

M0.3 is documentation-only. It creates no runtime data and requires no migration. Before dependent implementation, rollback is a Git revert; after dependent implementation, policy changes require a superseding ADR and an explicit data migration/rollback plan.
