# F0.2 Acceptance Contract — Postgres and Redis via Docker Compose

## Feature

Add resource-limited local Postgres and a Redis-protocol cache using Docker Compose, bind-mounted into the M0.3 data root at `data/services/{postgres,redis}`. Prove connectivity and that database migrations can run, without introducing any product schema — the first real table arrives with whichever feature first needs one.

## Scope decisions recorded before implementation

- **Active path: Docker Desktop.** Per the technical spec's P2/P3 ("pick one, not both") and `docs/decisions/0004`, WSL2-hosted Postgres/Redis remains the documented fallback only; it is not implemented. Docker Desktop was installed and its engine verified working during this feature (`docker info`, `docker compose version`).
- **Redis image: `valkey/valkey`, not `redis`.** Upstream Redis's license changed for versions 7.4+ (RSALv2/SSPLv1 dual license, not OSI-approved open source), which conflicts with this repository's own technical spec claiming all infrastructure is "Free / open source." Valkey is a BSD-3-Clause-licensed, wire-protocol-compatible fork (Linux Foundation), a drop-in replacement for every client library this project will use (`redis-py`, and Node/browser clients later). This is a container-image substitution only — no code, port, or protocol changes — and is trivially reversible by changing one image tag if the user prefers otherwise. `docs/architecture/data-lifecycle.md`'s `services/redis/` directory name is kept as-is since it names the *role* (Redis-protocol cache), not the vendor.
- **Resource limits (8 GB dev laptop, per correction C9):** Postgres 1 CPU / 512 MiB, Valkey 0.5 CPU / 256 MiB (matching the technical spec's own estimate of "~200–300 MB for a 25,000-instrument universe" for Redis). Set via Compose's legacy `mem_limit`/`cpus` keys, which plain `docker compose up` honors without Swarm mode.
- **No `.env.example` or central settings module here.** That is F0.4's explicit deliverable. Local-only, non-secret Postgres credentials are set directly as Compose environment defaults (never real Dhan credentials, never anything reachable outside the Docker network); the smoke tests read the same values from plain environment variables, not a settings abstraction.
- **Minimal Alembic scaffold, zero product schema.** `backend/alembic/` is initialized against `DATABASE_URL` so the migration *framework* is proven end-to-end (the plan's directory layout already names `backend/alembic/`), but the only revision is an empty bootstrap — no product table is created by this feature.
- **CI does not yet run live Postgres/Redis containers.** `.github/workflows/ci.yml` runs on `windows-latest`, which does not support Linux containers the way this Compose stack needs. The new integration tests skip cleanly (not silently pass) when the services aren't reachable, so CI stays green without them; provisioning a Linux-capable CI runner for these tests is flagged as a follow-up, not solved here.

## Required deliverables

1. `infra/docker-compose.yml`: `postgres` (official `postgres` image) and `valkey` (`valkey/valkey`) services, each with a healthcheck, resource limits, and a bind mount into `data/services/{postgres,redis}`.
2. `backend/alembic.ini` + `backend/alembic/env.py` + one empty bootstrap revision, configured to read `DATABASE_URL` from the environment.
3. `backend/tests/integration/test_docker_services.py`: Postgres connectivity (`SELECT 1`), `alembic upgrade head` succeeds and creates `alembic_version`, and Valkey connectivity (`SET`/`GET` round-trip) — each skipping with a clear reason if the corresponding service isn't reachable within a short timeout, never silently passing.
4. `pyproject.toml` updated with real runtime dependencies this feature needs: `psycopg[binary]`, `sqlalchemy`, `alembic`, `redis`.
5. Project-status update in `PROJECT_UPDATE.md` after implementation and after independent review.

## Acceptance scenarios

### A1 — `up` makes both healthy

- `docker compose -f infra/docker-compose.yml up -d` brings both services to a `healthy` status.
- `docker compose -f infra/docker-compose.yml down` cleanly stops them; the bind-mounted data directories persist under `data/services/` (gitignored, per M0.3).

### A2 — Connectivity and migrations pass on the 8 GB laptop

- With the stack up: `uv run pytest backend/tests/integration -q` passes all three integration tests (not skipped).
- `uv run alembic -c backend/alembic.ini upgrade head` succeeds against the running Postgres container and is idempotent (running it twice does not error).
- Both containers stay within their configured resource limits under this workload (`docker stats --no-stream` sampled once during the test run).

### A3 — Resource-limited and reversible

- `docker inspect` on each container shows the configured memory limit and CPU quota actually applied (not merely written in the compose file and ignored).
- Stopping/removing the stack (`docker compose down -v`) and re-running `up` reproduces a healthy stack from a clean state.

### A4 — Graceful skip when Docker isn't running

- With the stack down, `uv run pytest backend/tests/integration -q` reports the three tests as **skipped** with an explicit reason, and exits 0 — this is not the same as reporting them as passing, and the skip reason must name the missing service.

## Verification

- All commands in A1–A4, exact output recorded in the completion report.
- `uv run ruff check .`, `uv run mypy backend --strict`, `uv run pytest` (full suite, services down — confirms A4 and that nothing else regressed).
- `git diff --check`, secret-shaped-content scan (the local dev Postgres password is not secret-shaped in the sense of being a real credential, but is still scanned for consistency), and local Markdown link resolution.
- Confirm `build/validate_manifest.py` and `build/validate_fixtures.py` are unaffected.

## Non-goals

- No product schema/tables — the first real table belongs to whichever feature needs it first.
- No `.env.example`, secret redaction, or settings module — F0.4.
- No `api`/`engine`/`feedd`/`worker` process code — F0.3.
- No production/Lightsail Docker deployment — Epic 13.
- No CI-hosted live-container integration testing — flagged as a follow-up.

## Migration and rollback

New files and local Docker state only; no product schema or runtime market data. `docker compose down -v` removes all container state including the bind-mounted `data/services/{postgres,redis}` directories' *contents* (the directories themselves are local dev state, not backed up — consistent with `data-lifecycle.md` marking `services/redis/` reconstructible and `services/postgres/` durable only "through tested database backup," which does not exist until Epic 13). Revert the F0.2 commit(s) to roll back before F0.3 depends on the process skeletons this stack will eventually back.
