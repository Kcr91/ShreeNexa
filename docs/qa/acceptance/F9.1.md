# F9.1 Acceptance Contract — PaperBroker Using Live Data Source, Realistic Fill Policy, Persisted Orders/Fills, and Restart Recovery

## Feature

Production-grade `PaperBroker` executing paper trades against live ticks/bars with realistic fill simulation (Market, Limit, Stop, Stop-Limit with slippage and Indian statutory transaction costs), persistent state management, and restart recovery with fill idempotency.

## Scope decisions recorded before implementation

- **Order Types & Realistic Fill Models (Spec §9.1)**:
  - Market Orders: Immediate fill on next tick/bar with slippage.
  - Limit Orders: Fills only when market price reaches or penetrates limit price ($P_{\text{ask}} \le P_{\text{limit}}$ for BUY, $P_{\text{bid}} \ge P_{\text{limit}}$ for SELL).
  - Stop Orders: Triggers into Market order once trigger price is crossed.
  - Stop-Limit Orders: Triggers into Limit order once trigger price is crossed.
- **Transaction Costs & Slippage**:
  - Automatically factors in STT, GST, SEBI turnover fees, and stamp duty via `IndianCostModel`.
- **State Machine Properties**:
  - Rigorous lifecycle: `SUBMITTED -> ACCEPTED -> FILLED | PARTIALLY_FILLED | CANCELLED | REJECTED | EXPIRED`.
- **Restart Recovery & Idempotency Invariants (Proof G1)**:
  - All orders, fills, positions, and accounts persist to repository.
  - On engine restart or event replay, `PaperBroker.recover()` reconstitutes the portfolio and rejects any duplicate fill IDs.
  - **Invariance Rule**: Replaying identical ticks/bars or re-running recovery must NEVER produce duplicate fills or double-count portfolio cash/positions.
- **REST API Endpoints**:
  - `POST /api/v1/paper/accounts`
  - `GET /api/v1/paper/accounts/{id}`
  - `POST /api/v1/paper/orders`
  - `DELETE /api/v1/paper/orders/{id}`
  - `GET /api/v1/paper/orders`
  - `GET /api/v1/paper/positions`
  - `GET /api/v1/paper/fills`

## Required deliverables

1. `backend/app/paper/models.py` — Data models for accounts, orders, fills, and positions.
2. `backend/app/paper/fill_policy.py` — Realistic fill matcher (Market, Limit, Stop, Stop-Limit, Slippage).
3. `backend/app/paper/repository.py` — Persistent storage repository for paper state.
4. `backend/app/paper/broker.py` — `PaperBroker` state-machine and recovery engine.
5. `backend/app/api/paper.py` — REST API router for paper trading accounts, orders, positions, and trades.
6. `backend/tests/unit/test_paper_broker_recovery.py` — Comprehensive unit and state-machine tests for fill policy, idempotency, restart recovery, and REST API.
7. `docs/qa/acceptance/F9.1.md` — Acceptance contract.
