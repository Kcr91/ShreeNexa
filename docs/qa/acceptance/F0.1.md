# F0.1 Acceptance Contract — Repository Standardization

## Feature

Standardize the repository's Python and Node tooling: a `uv`-managed Python 3.14 environment and lockfile for `backend/` and the existing `build/` scripts, ruff/mypy/pytest configuration, a Node/npm workspace skeleton for `frontend/` (tooling only — no product UI, that is F4.1), a `pre-commit` configuration wiring the fast checks, and a CI workflow skeleton running the same gates. No trading behavior, product feature, or database dependency is introduced.

## Scope decisions recorded before implementation

- **Python dependency/lockfile manager: `uv`** (user decision, 2026-08-31), per `docs/decisions/0004-packages-and-windows-topology.md`, which explicitly deferred this choice to F0.1. One shared `.venv` at the repository root, one root `pyproject.toml`/`uv.lock`, per that ADR's "the project environment will be `F:\ShreeNexa\.venv`."
- **Node package manager: `npm`** — already implied throughout `AGENTS.md` and the build plan's canonical commands (`npm.cmd --prefix frontend run ...`); not re-litigated here.
- **CI platform: GitHub Actions** (`.github/workflows/ci.yml`) — the repository has no remote configured yet, so this workflow is inert until one exists. Chosen as the default, low-cost, easily-replaced option; not a decision that commits to a specific host, since the file does nothing without a remote.
- **`build/` stays unpackaged.** Per ADR-0004, `build/` is "repository-local, not published." Its scripts (`validate_manifest.py`, `validate_fixtures.py`, `update_state.py`, `state_schema.py`) keep running as plain scripts, not an installable package; they draw their runtime dependencies (currently only PyYAML) from the same shared root venv as `backend/`.
- **Frontend is tooling-only in F0.1.** `frontend/package.json` and its `typecheck`/`test`/`build` scripts must exist and pass, but the app itself is a placeholder — F4.1 builds the real shell, routing, and API client boundary.

## Required deliverables

1. Root `pyproject.toml` (project `shreenexa-backend`, `requires-python == 3.14.*`, `backend/app` as the wheel's package target) plus `.python-version` pinning `3.14`.
2. `uv.lock` generated from that `pyproject.toml`, committed, reproducing an identical environment on `uv sync`.
3. `[tool.ruff]`, `[tool.mypy]` (strict, targeting `backend`), and `[tool.pytest.ini_options]` (covering both `backend/tests` and `build/tests`) configuration.
4. Minimal `backend/app/__init__.py` (version stub only — no product code) and `backend/tests/unit/test_app_package.py` proving the test layer itself works end to end.
5. `frontend/package.json` with `typecheck`, `test`, `build` npm scripts backed by a minimal Vite + TypeScript + Vitest skeleton (one placeholder component/test), and `frontend/package-lock.json`.
6. `.pre-commit-config.yaml` wiring ruff (lint + format), standard hygiene hooks (trailing whitespace, end-of-file, YAML/JSON/TOML syntax, large-file guard), and local hooks running `build/validate_manifest.py` and `build/validate_fixtures.py` so a manifest or fixture edit can't silently go stale.
7. `.github/workflows/ci.yml` running, on push/PR: `uv sync`, ruff, mypy, pytest (backend + build), `build/validate_manifest.py`, `build/validate_fixtures.py`, and the frontend `typecheck`/`test`/`build` scripts.
8. `AGENTS.md` updated: the "become mandatory after F0.1" backend/frontend commands move to the "checks available now" list, with `uv run` prefixes where applicable.
9. Project-status update in `PROJECT_UPDATE.md` after implementation and after independent review.

## Acceptance scenarios

### A1 — Clean checkout installs from locks

- `uv sync` on a fresh clone reproduces the locked environment with no manual dependency resolution.
- `npm ci --prefix frontend` on the same fresh clone installs frontend dependencies from `package-lock.json` with no version drift.

### A2 — CPython 3.14 binary-wheel check

- Every dependency `uv sync` resolves has an available `cp314`-compatible wheel (or is pure Python) for `win_amd64` — `uv sync` itself is the check: it fails loudly if it must build from source unexpectedly.

### A3 — Every baseline command passes

- `uv run ruff check .`
- `uv run mypy backend --strict`
- `uv run pytest` (discovers and passes both `backend/tests` and `build/tests`)
- `npm --prefix frontend run typecheck`
- `npm --prefix frontend run test`
- `npm --prefix frontend run build`
- `python build/validate_manifest.py` and `python build/validate_fixtures.py` still pass unchanged (F0.1 does not touch the manifest or fixtures).

### A4 — Pre-commit and CI actually catch something

- Running `pre-commit run --all-files` on the clean tree passes.
- A deliberately introduced ruff violation, and a deliberately corrupted `build/manifest.yaml`, are each shown to be caught by `pre-commit run --all-files` before being reverted.

## Verification

- All commands in A1–A4, with exact output/exit codes recorded in the completion report.
- `git diff --check`, a secret-shaped-content scan, and local Markdown link resolution across the changed files.
- Confirm no protected path, database, or live-trading code is introduced.
- Confirm `build/validate_manifest.py` and `build/validate_fixtures.py` still report their unchanged M0.5/M0.6 results (108 items / 2 fixtures).

## Non-goals

- No FastAPI app, database connection, or Dhan client — those are F0.2–F0.5.
- No real frontend UI, routing, or API client — that is F4.1.
- No Docker Compose / Postgres / Redis — that is F0.2.
- No GitHub remote is created or pushed to; the CI workflow is added but not exercised.

## Migration and rollback

New files and configuration only; no schema or runtime-data impact. Revert the F0.1 commit(s) to roll back before F0.2 depends on this environment.
