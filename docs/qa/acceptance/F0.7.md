# F0.7 Acceptance Contract — Detailed Dhan Instrument Master Ingestion and Typed Search

## Feature

Ingest the detailed Dhan instrument master CSV, persist records in PostgreSQL with composite primary key `(exchange_segment, security_id)` and indexes, dynamically discover all exchange segments present in the source without hardcoded assumptions, and expose a typed search and option-chain lookup API.

## Scope decisions recorded before implementation

- **PostgreSQL Schema & Ingestion**:
  - `instrument` table stores all fields: `security_id`, `exchange_segment`, `instrument_type`, `symbol`, `trading_symbol`, `isin`, `lot_size`, `tick_size`, `expiry_date`, `strike_price`, `option_type`, `underlying_id`, `is_active`, `raw` (JSONB), and `synced_at`.
  - Primary key is composite: `(exchange_segment, security_id)`.
  - Index on `symbol`, composite index on `(underlying_id, expiry_date, strike_price)` for fast option chain querying.
  - Bulk upsert via PostgreSQL `ON CONFLICT (exchange_segment, security_id) DO UPDATE` ensures daily synchronization is idempotent.
- **Dynamic Segment Discovery**:
  - Does NOT hardcode assumption "7" or static segment numbers if the master disagrees (per build plan C10 & manifest F0.7).
  - Normalizes segments dynamically (`IDX_I`, `NSE_EQ`, `NSE_FNO`, `NSE_CURRENCY`, `BSE_EQ`, `MCX_COMM`, `BSE_CURRENCY`, `BSE_FNO`, and any novel segment code).
- **Schema Drift & Error Tolerance**:
  - Handles variations in CSV header casing and names (e.g., `SEM_SMST_SECURITY_ID` vs `SECURITY_ID`, `SEM_CUSTOM_SYMBOL` vs `SYMBOL`).
  - Skips corrupted rows with non-numeric IDs without failing the entire batch, recording counts in `IngestSummary`.
  - Parses dates in standard `YYYY-MM-DD` and `DD-Mon-YYYY` formats.
- **Typed Search API**:
  - Search by prefix/substring on `symbol`, `trading_symbol`, or exact `security_id`.
  - Filter by `exchange_segment`, `instrument_type`, `underlying_id`, `expiry_date`, `strike_price`, `option_type`, and `is_active`.
  - Option chain retrieval ordered by strike price.
  - Distinct segment listing.

## Acceptance scenarios

### A1 — Database migration reversibility
- `alembic upgrade head` creates the `instrument` table with composite primary key and indexes.
- `alembic downgrade -1` cleanly drops the table and indexes.

### A2 — Dynamic segment resolution and CSV parsing
- Parser correctly processes equities, futures, index options, stock options, commodities, and currencies across all segments.
- Unrecognized or future segment codes are preserved without crashing.

### A3 — Idempotent bulk upsert
- Re-ingesting the same master updates `synced_at` and updated attributes without duplicate key violations or row multiplication.

### A4 — Typed symbol and option search
- Search query `NIFTY` returns index, futures, and option contracts.
- Filter by `exchange_segment="NSE_EQ"` returns only cash equities.
- Option chain query for `underlying_id` and `expiry_date` returns all calls (`CE`) and puts (`PE`) sorted by strike price.

### A5 — Fault tolerance and schema drift
- Malformed rows, empty security IDs, or altered CSV header casing are handled gracefully without terminating batch ingestion.

### A6 — REST API contract
- `GET /api/v1/instruments/search` returns filtered `list[InstrumentRecord]`.
- `GET /api/v1/instruments/segments` returns all distinct segments in the database.
- `GET /api/v1/instruments/{exchange_segment}/{security_id}` returns exact instrument or 404.
