# F13.2 Acceptance Contract: Lightsail Mumbai Provisioning, Network Policy, Systemd/Container Supervision, Caddy TLS, and Blue/Green Upstream

## Feature Definition
- **Feature ID**: F13.2
- **Name**: Lightsail Mumbai provisioning, network policy, systemd/container supervision, Caddy TLS, and blue/green upstream.
- **Dependencies**: F13.1
- **Proof Requirement**: Staging deploy/rollback runbook is executed; only intended public ports are reachable.

## Invariants & Acceptance Criteria

1. **Lightsail Mumbai Provisioning & Network Policy (`infra/lightsail/`)**:
   - Provisioning scripts targeting AWS Lightsail in Mumbai (`ap-south-1`).
   - Network Policy & Firewall:
     - Public ports allowed: 80 (HTTP redirect), 443 (HTTPS TLS), and 22 (SSH - key-based authentication only).
     - Strict isolation: Ports 5432 (Postgres), 6379 (Valkey/Redis), 8000/8001 (API blue/green upstreams), 8080/8081/8082 (Sandbox) are bound strictly to localhost or internal docker network. Any external ingress is rejected by policy.
   - System limits & kernel tuning (`nofile`, tcp buffers) appropriate for high-throughput WebSocket streams.

2. **Caddy TLS & Reverse Proxy Architecture (`infra/caddy/`)**:
   - Automated TLS certificate management with ACME / Let's Encrypt.
   - Reverse proxy routing for API endpoints and persistent WebSockets (`/ws`, `/api/v1/ws`).
   - Hardened HTTP security headers: HSTS (`Strict-Transport-Security`), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`.
   - Upstream configuration pointing to active blue or green instance (`127.0.0.1:8000` or `127.0.0.1:8001`).
   - Zero-downtime hot reloading via `caddy reload`.

3. **Blue/Green Deployment & Rollback Controller (`infra/lightsail/blue_green.py`)**:
   - Manages zero-downtime deployment for the stateless `api` service.
   - Detects currently active color (`blue` on 8000 or `green` on 8001).
   - Starts candidate container on the opposite, inactive port.
   - Executes pre-traffic health check probe against `/healthz`.
   - Flips Caddy upstream configuration to candidate color and reloads Caddy without dropping active connections.
   - Drains previous container gracefully and stops it.
   - Automatic rollback: if health check fails or promotion errors, the deployment immediately aborts, Caddy remains pointing to the previous healthy container, and the failed candidate is pruned.
   - Critical Invariant: Background daemons (`engine`, `feedd`, `worker`) run under persistent supervision and are NOT restarted during blue/green API promotions or rollbacks.

4. **Staging Deploy / Rollback Runbook (`docs/runbooks/staging-deploy-rollback.md`)**:
   - Step-by-step verified procedure for staging deployment, health verification, upstream flipping, and emergency rollback.
   - Explicit port verification procedures confirming only 80, 443, and 22 are reachable.

5. **Quality & Boundary Compliance**:
   - Zero modifications to protected paths (`backend/app/engine/risk.py`, `backend/app/engine/broker.py`, `backend/app/dhan/orders.py`, `backend/tests/parity/`).
   - Zero secrets or private keys in scripts or repositories.
   - Comprehensive unit and integration test suite validating network policy, Caddyfile configuration, blue/green state machine, and automated rollback.
