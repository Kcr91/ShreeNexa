# M0.4 Acceptance Contract — Repository Guidance and QA Rules

## Feature

Add root project instructions, narrow trusted-project Codex configuration, architecture/QA navigation, protected-path policy, and the feature completion-report contract.

## Required deliverables

1. Root `AGENTS.md` that a fresh Codex session can use without repository-wide exploration.
2. Narrow `.codex/config.toml` using only current documented keys and no broad permissions.
3. Documentation for QA layers, cross-cutting gates, protected paths, feature workflow, and completion reporting.
4. Architecture and QA indexes linking the authoritative documents.
5. Project-status updates after implementation and review.

## Acceptance scenarios

### A1 — Fresh-session orientation

From `AGENTS.md` alone, a new session can identify:

- repository purpose and current greenfield status;
- the source-of-truth plan/specification and relevant architecture/QA indexes;
- the forbidden legacy-project boundary;
- branch, scope, contract-first, review, and merge rules;
- currently available checks and future canonical backend/frontend gates;
- secrets, data, live-trading, and protected-path restrictions;
- the exact completion-report fields and stop conditions.

### A2 — Narrow Codex configuration

- Configuration parses as TOML using the installed Python standard library.
- Sandbox mode is workspace-write, not danger-full-access.
- Approval policy remains interactive.
- Workspace-sandbox network access is disabled.
- No model, provider, MCP server, credential, external writable root, or live capability is configured.
- The file explains that project configuration loads only when the user trusts the repository.

### A3 — Protected paths

- `backend/app/engine/risk.py`, `backend/app/engine/broker.py`, `backend/app/dhan/orders.py`, and `backend/tests/parity/` are named exactly.
- Unattended/automated work must not modify them.
- A supervised protected-path change requires explicit scope, its own branch, targeted tests, independent review, and a protected-diff check.
- No rule implies permission to place a real order.

### A4 — QA and completion

- L1–L5 and G1–G6 are defined consistently with the approved specification.
- Commands distinguish active checks from commands that become active after F0.1 scaffolding.
- The completion report contains branch/commit, files, behavior, schema impact, exact tests, manual validation, limitations, and merge readiness.
- Documentation-only work has a proportional but explicit validation path.

## Verification

- Parse `.codex/config.toml` with `python -c "import tomllib, pathlib; tomllib.loads(pathlib.Path('.codex/config.toml').read_text(encoding='utf-8'))"`.
- Check `AGENTS.md` remains below the documented 32 KiB instruction limit.
- Verify every protected path and completion-report field appears in both the concise instructions and detailed QA documentation.
- Resolve local Markdown links, scan for secret-shaped content, and run `git diff --check`.
- Confirm no product package, dependency, hook, rule script, or runtime data was introduced.

## Non-goals

- No backend/frontend scaffolding or dependencies.
- No automated Codex runner, hooks, or feature manifest; those belong to later features.
- No bypass of user-level, managed, or sandbox security policy.
- No live-order implementation or activation.

## Migration and rollback

Documentation/configuration only. Revert the M0.4 commit to roll back before dependent work. Later changes to protected-path or safety rules require an independently reviewed feature rather than an incidental edit.
