# F0.4 Acceptance Contract — Central Settings, Secret Redaction, and Dhan Token Health

## Feature

Implement type-safe central configuration (`backend/app/config.py`, `.env.example`), secure secret loading with automatic redaction, Windows DPAPI local credential persistence with no plaintext fallback (per ADR-0006), and a Dhan token-expiry health monitoring state and banner API.

## Scope decisions recorded before implementation

- **Settings Engine**: Central configuration uses `pydantic-settings` (`BaseSettings`) loading from environment variables and `.env`. Default values provide safe local defaults for development (`127.0.0.1:5432` Postgres, `127.0.0.1:6379` Redis).
- **Secret Redaction**: Secrets (`DHAN_ACCESS_TOKEN`, database passwords, etc.) are typed with `pydantic.SecretStr`. String conversion, object representations (`repr`), structured logs, exception messages, and frontend API payloads MUST NEVER expose raw secret values, rendering `[REDACTED]` or `**********` instead.
- **Local Credential Storage with Windows DPAPI**: Per ADR-0006, local development credentials (Dhan Client ID, Access Token, and Token Expiry timestamp) can be persisted locally using Windows Data Protection API (`CryptProtectData`/`CryptUnprotectData`) scoped exclusively to the current Windows user (`CRYPTPROTECT_UI_FORBIDDEN`, no `CRYPTPROTECT_LOCAL_MACHINE`). Storage lives under an ignored runtime root (`.runtime/credentials/dhan.enc`) with strict user permissions.
- **No Plaintext Fallback**: There is NO plaintext intermediate file, plaintext fallback, or fallback to unencrypted local files. If DPAPI is unavailable (e.g. non-Windows environment), configuration relies strictly on environment variables or a test-scoped in-memory fake.
- **24-Hour Dhan Web Token Lifetime**: Per official Dhan v2 documentation and ADR-0006, manually generated Dhan Web access tokens are valid for 24 hours. When an absolute expiry timestamp is supplied, it is preserved across application restarts; restarts never synthesize a new `now + 24 hours`.
- **Token Health States**: The system evaluates token health into explicit states:
  - `valid`: Token present and > 2 hours remaining before expiry.
  - `expiring_soon`: Token present and <= 2 hours remaining before expiry.
  - `expired`: Token present but expiry timestamp is in the past.
  - `unknown_expiry`: Token present but no valid expiry metadata was provided.
  - `missing`: No client ID or access token configured.
  - `revoked`: Explicitly marked as revoked or rejected by authentication.
- **Non-Secret Banner API**: FastAPI exposes `/api/v1/dhan/token-health` returning only non-secret metadata: `status`, `expires_at` (UTC ISO string), `expires_in_seconds`, `client_id_masked` (e.g. `1100***123`), and `is_valid`. The raw access token is never included in the response.

## Required deliverables

1. `.env.example` — Complete template with non-secret defaults and placeholders for all environment variables (`DATABASE_URL`, `REDIS_URL`, `DHAN_CLIENT_ID`, `DHAN_ACCESS_TOKEN`, `DHAN_TOKEN_EXPIRES_AT`, `ENVIRONMENT`, `LOG_LEVEL`).
2. `backend/app/config.py` — Central Pydantic `Settings` class with `SecretStr` fields, validation, and secret redaction utilities (`redact_text`, `mask_credential`).
3. `backend/app/dhan/dpapi.py` — Native Windows DPAPI adapter utilizing `ctypes` (`CryptProtectData`, `CryptUnprotectData`), scoped to the current user with no `CRYPTPROTECT_LOCAL_MACHINE`, and a fake adapter for automated test isolation.
4. `backend/app/dhan/credentials.py` — Dhan credential resolver with precedence: environment variables > local encrypted DPAPI storage > none.
5. `backend/app/dhan/health.py` — Token health calculator supporting 24-hour lifetime, IST/UTC timezone conversions, remaining time calculations, and state determinations (`valid`, `expiring_soon`, `expired`, `unknown_expiry`, `missing`, `revoked`).
6. `backend/app/dhan/__init__.py` — Package export.
7. `backend/app/main.py` — Updated FastAPI application registering the `/api/v1/dhan/token-health` endpoint and secret redaction middleware/exception formatting.
8. `backend/tests/unit/test_config.py` — Unit tests for settings parsing, env override precedence, `SecretStr` redaction in `repr`/`str`/logs.
9. `backend/tests/unit/test_dpapi.py` — Unit tests for DPAPI encryption/decryption, tampered payload rejection, and current-user storage isolation.
10. `backend/tests/unit/test_dhan_token_health.py` — Unit tests for all token health states, timezone handling, restart persistence, and API payload safety.

## Acceptance scenarios

### A1 — Central settings and environment precedence
- `Settings()` loads default configuration when no environment variables or `.env` are present.
- Environment variables override default settings.
- Database passwords and Dhan access tokens are loaded as `SecretStr`.

### A2 — Automatic secret redaction
- Printing `settings`, converting to string `str(settings)`, or inspecting `repr(settings)` outputs `[REDACTED]` or `**********` for all secrets.
- Redaction helper replaces token-like and password-like substrings in raw error messages and log records.

### A3 — Windows DPAPI local credential storage
- `dpapi.protect(data)` and `dpapi.unprotect(encrypted)` correctly round-trip byte payloads on Windows.
- Calling `unprotect` on tampered or corrupted ciphertext raises a descriptive error.
- Credentials stored via `save_credentials` write only encrypted bytes to disk under `.runtime/credentials/dhan.enc`.

### A4 — Dhan token-expiry health states and timezone handling
- A token expiring in > 2 hours produces status `valid` with correct `expires_in_seconds`.
- A token expiring in <= 2 hours produces status `expiring_soon`.
- A token with past expiry produces status `expired`.
- A token with no expiry metadata produces status `unknown_expiry`.
- Absence of credentials produces status `missing`.
- Expiry timestamps parsed from IST (`+05:30`) or UTC strings convert deterministically to UTC.
- Restarting the application preserves the original absolute expiry timestamp.

### A5 — Non-secret token health banner API
- `GET /api/v1/dhan/token-health` returns 200 with JSON payload containing `status`, `is_valid`, `expires_at`, `expires_in_seconds`, and masked client ID.
- The response JSON payload NEVER contains `DHAN_ACCESS_TOKEN` or any raw secret.

## Non-goals

- No real Dhan API calls, credential validation network requests, or token generation.
- No PIN, password, TOTP seed, browser cookie, API key, or API secret storage.
- No live broker connection or order placement.
- No plaintext credential file fallback.
- No protected-path code (`engine/risk.py`, `engine/broker.py`, `dhan/orders.py`).
