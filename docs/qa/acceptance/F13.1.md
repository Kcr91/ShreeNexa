# F13.1 Acceptance Contract: Production Containers for API, Engine, Feedd, and Worker

## Feature Definition
- **Feature ID**: F13.1
- **Name**: Production containers for api, engine, feedd, and worker, with non-root users, health checks, resource limits, and immutable images.
- **Dependencies**: F9.1, F9.2, F9.3, F9.4, F9.5, F9.6, F9.7
- **Proof Requirement**: Local production stack starts cleanly; restarting API leaves engine/paper deployment intact.

## Invariants & Acceptance Criteria

1. **Multi-Stage Hardened Production Dockerfile (`infra/Dockerfile`)**:
   - Multi-stage build targeting CPython 3.14 on Linux slim/distroless.
   - Non-root user: dedicated system account `shreenexa` (UID/GID 10001) with zero `sudo`/root privileges.
   - Minimal attack surface: zero build tools (gcc, make) in runtime stage.
   - Separate entrypoint targets or single unified image supporting:
     - `api`: FastAPI application via `uvicorn app.main:app --host 0.0.0.0 --port 8000`.
     - `engine`: Paper/live execution loop via `python -m app.engine.core`.
     - `feedd`: Market data feed and subscription daemon via `python -m app.feedd.core`.
     - `worker`: Historical warehouse ingest and backfill publisher via `python -m app.worker.core`.

2. **Immutable Production Compose Stack (`infra/docker-compose.prod.yml`)**:
   - Declares isolated production services: `postgres`, `valkey`, `api`, `engine`, `feedd`, `worker`.
   - Immutable image tags pinning exact semantic releases (`shreenexa/api:prod`, etc.).
   - Explicit resource limits configured on every service:
     - `api`: max 1.0 CPU, 512MB RAM.
     - `engine`: max 2.0 CPU, 1024MB RAM.
     - `feedd`: max 1.0 CPU, 512MB RAM.
     - `worker`: max 1.0 CPU, 512MB RAM.
   - Non-root security context (`user: "10001:10001"`).
   - Read-only root filesystem security where possible with dedicated `/tmp` and `/app/data` tmpfs mounts.

3. **Production Health Checks**:
   - Every service defines an automated, non-flaky health check:
     - `api`: HTTP probe (`curl -f http://localhost:8000/healthz || exit 1` or Python probe).
     - `engine`: Process and durable heartbeat probe (`python -m app.contracts.health_check engine`).
     - `feedd`: Heartbeat probe (`python -m app.contracts.health_check feedd`).
     - `worker`: Heartbeat probe (`python -m app.contracts.health_check worker`).
   - Start periods, intervals, and timeouts explicitly bounded.

4. **Proof Invariant: Process Independence & Zero API Coupling**:
   - Restarting `api` container does NOT restart `engine` container.
   - Active paper deployments and live strategy loops running inside `engine` maintain continuous heartbeat and execution state across API restarts.
   - No container depends on `api` to start or run (`engine`, `feedd`, and `worker` depend only on `postgres` and `valkey`).

5. **Quality & Boundary Compliance**:
   - Zero edits to protected paths (`backend/app/engine/risk.py`, `backend/app/engine/broker.py`, `backend/app/dhan/orders.py`, `backend/tests/parity/`).
   - Zero hardcoded secrets in Dockerfile or compose files.
   - Automated test suite validating Dockerfile and docker-compose configurations, non-root user enforcement, health checks, resource limits, and process independence.
