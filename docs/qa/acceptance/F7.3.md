# F7.3 Acceptance Contract — Redis Quote, OI, and Depth Hot Cache

## Feature

Redis quote/OI/depth hot cache with schema/version, freshness, and feed-health records.

## Scope decisions recorded before implementation

- **Storage Ownership & Role (ADR-0003)**:
  - `feedd` is the sole write owner of quotes, OI, depth, and feed health hot records.
  - `api`, `engine`, and `worker` read from the hot cache.
  - Data is reconstructible hot state; loss of Redis does not corrupt permanent state.
- **Key Namespacing & Versioning**:
  - `CACHE_SCHEMA_VERSION = 1`.
  - Namespaces:
    - Quote: `shreenexa:feed:v1:quote:{segment}:{security_id}`
    - OI: `shreenexa:feed:v1:oi:{segment}:{security_id}`
    - Depth: `shreenexa:feed:v1:depth:{segment}:{security_id}`
    - Health: `shreenexa:feed:v1:health:{socket_id}`
- **Freshness & Stale Data Invariant**:
  - Configurable `freshness_threshold_seconds: float = 5.0`.
  - Every cached record stores `received_at: float` (UTC epoch timestamp).
  - Upon read, if `(now - received_at) > freshness_threshold_seconds`:
    - The record is marked `is_stale = True`.
    - Staleness duration is calculated and reported in `staleness_seconds`.
    - Stale data is never presented as live (`is_stale` is never False for expired data).
- **Atomicity & Batching**:
  - Updates from composite packets (e.g. `FullPacket` containing Quote, 5-level Depth, and OI) write atomically via Redis pipeline.
  - Multi-instrument reads (`get_multi_quotes`) use batch pipelines to minimize round-trips.
- **HotCache Abstraction & Testability**:
  - `HotCache(Protocol)` implemented by `RedisHotCache` (using Redis client) and `InMemoryHotCache` (for testing without external service dependency).

## Acceptance scenarios

### E1 — Ingestion of Quote, OI, and Full packets
- Updating cache with a `QuotePacket` stores all quote fields with current timestamp and schema version.
- Updating cache with an `OIPacket` stores open interest.
- Updating cache with a `FullPacket` atomically updates Quote, 5-level Depth ladder, and OI in a single operation.

### E2 — Freshness verification and stale data marking
- A record read within `freshness_threshold_seconds` has `is_stale is False`.
- A record read after `freshness_threshold_seconds` has `is_stale is True` and `staleness_seconds > 5.0`.
- Stale data is never presented as live under any timing condition.

### E3 — Multi-instrument batch query
- Querying 50 symbols returns a mapping of all found cached quotes in a single batched pipeline call.
- Missing symbols are gracefully omitted from results without error.

### E4 — Feed health records
- Feed health records reflect socket connection state, subscribed count, packet counts, and timestamps.
- Aggregated health queries return all socket records.
