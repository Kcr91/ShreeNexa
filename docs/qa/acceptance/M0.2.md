# M0.2 Acceptance Contract — Greenfield Architecture

## Feature

Freeze the greenfield architecture, process boundaries, storage ownership, package names, and Windows development topology as reviewed architecture decisions.

## Inputs

- `SHREENEXA_TECHNICAL_SPEC.md` version 1.1.
- `SHREENEXA_CODEX_VSCODE_BUILD_PLAN.md` dated 2026-08-31.
- M0.1 environment audit and reviewed repository baseline.

## Required deliverables

1. Accepted ADRs covering:
   - repository and legacy-project isolation;
   - four-process runtime boundaries and supervision;
   - storage ownership and authoritative-state rules;
   - package names, dependency direction, and the Windows development topology.
2. A module/dependency map with an explicit directed acyclic graph.
3. A single-writer/owner table for mutable state and external connections.
4. An architecture index linking every M0.2 decision.
5. A project-status update recording completion evidence and remaining blockers.

## Acceptance scenarios

### A1 — Greenfield isolation

- No runtime package, data path, environment variable, or tool configuration depends on `F:\Algotrading`.
- References to the legacy path are permitted only to document and enforce that prohibition.
- All future local data belongs below the repository or a separately configured ShreeNexa-only data root defined in M0.3.

### A2 — Process ownership

- `api`, `engine`, `feedd`, and `worker` have distinct responsibilities.
- Restarting `api` cannot imply restarting `engine`.
- No process holds authoritative trading or job state only in memory.
- Dhan socket ownership is assigned to `feedd`; order execution is assigned to `engine` through a broker boundary.

### A3 — Storage ownership

- Postgres is authoritative for transactional/domain state.
- Redis contains reconstructible hot state, coordination primitives, and queues; it is not the system of record for orders, fills, positions, or strategies.
- DuckDB/Parquet owns immutable historical market data and has an explicit single-writer workflow.
- Frontend and browser clients never access a storage engine directly.

### A4 — Dependency direction

- The documented module graph is acyclic.
- Domain and contract modules do not import process entry points, transport adapters, or UI code.
- Process entry points compose dependencies at the outer edge.
- Cross-process communication uses versioned contracts rather than importing another process's entry point.

### A5 — Windows topology

- Native Windows is the single development environment for this working tree.
- Python 3.14 and Node 24 are the recorded targets from M0.1.
- Docker Desktop is the selected Postgres/Redis path once installed; WSL remains an explicit fallback and is not mixed into the same checkout.
- Runtime data, logs, secrets, and generated output remain outside version control.

## Verification

- Review every ADR status and link from the architecture and decision indexes.
- Inspect the dependency graph for a topological ordering and circular ownership.
- Search new architecture files for accidental legacy-project integration language.
- Run `git diff --check` and a secret-pattern scan.
- Confirm the final worktree contains only the intended M0.2 files.

## Non-goals

- No backend or frontend package scaffolding.
- No dependency installation or lockfiles.
- No Docker, Postgres, Redis, DuckDB, or Parquet setup.
- No final data-root or backup policy; that is M0.3.
- No `AGENTS.md`, `.codex/config.toml`, manifest, or `build/state.json`; those are M0.4–M0.5.
- No Dhan calls, credentials, trading behavior, or live-order path.

## Migration and rollback

M0.2 is documentation-only and has no schema or runtime migration. Rollback consists of reverting the M0.2 documentation commit before dependent features are implemented; after dependent features exist, supersede decisions with new ADRs rather than rewriting accepted history.
