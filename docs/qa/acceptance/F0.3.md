# F0.3 Acceptance Contract — Process Skeletons and Supervisor Contract

## Feature

Create the four independent runtime process entry points named by ADR-0002 (`api`, `engine`, `feedd`, `worker`), each with no trading behavior yet, plus a durable heartbeat contract proving they are genuinely independent processes (not just functions sharing one process). Select and implement the local-Windows-dev supervisor mechanism ADR-0002 deferred to this feature.

## Scope decisions recorded before implementation

- **Namespaces**: `app.feedd` and `app.worker` are new top-level capability namespaces, added because F0.3 is the feature that first needs them — consistent with `docs/decisions/0004`'s "created only when a feature needs them." `app.engine`'s entry point is `core.py`, matching the technical spec's directory layout exactly. Console-script wiring lives in `app.cli` (already an approved namespace: "management commands").
- **Command names are exactly `api`, `engine`, `feedd`, `worker`**, per ADR-0004 ("without renaming these roles"), wired via `[project.scripts]` in `pyproject.toml`.
- **Supervisor**: a minimal custom Python process supervisor (`app.cli.supervisor`, console-scripted as `supervisor`), not NSSM or a Windows Service. Local dev on Windows doesn't need a production service manager (that's Epic 13's containerized/systemd deployment on Linux); a small `subprocess`-based supervisor that starts all four roles and restarts one on unexpected exit is enough to prove ADR-0002 invariant 6 ("the supervisor starts and observes processes independently") without adding an external system dependency.
- **Durable heartbeat, not in-memory liveness.** Per ADR-0002 invariant 2 ("No process holds authoritative ... only in memory"), each process's liveness is proven via a Postgres `process_heartbeat` row (this feature's first real product table), not merely by the OS reporting the PID exists. This is also the concrete mechanism for the proof scenario: killing `api` must be observable as *not* affecting `engine`'s row.
- **No settings module.** `DATABASE_URL` is read directly from the environment in each process, matching F0.2's pattern. `app.config` (central settings, `.env.example`, secret redaction) is F0.4's explicit deliverable — not duplicated here.
- **No real capability logic.** `feedd` does not connect to Dhan (F0.5–F0.7), `worker` does not run real jobs (Epic 1+), `engine` does not run a strategy loop (F3.1+), `api` exposes only a health/heartbeat endpoint. Each process's loop body is the heartbeat write; nothing else.

## Required deliverables

1. `backend/app/contracts/heartbeat.py` — the shared heartbeat read/write contract (SQLAlchemy Core, no ORM needed for one table) used by all four processes and by tests.
2. Alembic revision creating `process_heartbeat(process_name PK, pid, status, started_at, last_heartbeat_at)`.
3. Four process entry points, each: connects using `DATABASE_URL`, upserts its heartbeat row on startup (`status='running'`), updates `last_heartbeat_at` every ~1s, handles `SIGINT`/`SIGTERM` by setting `status='stopped'` and exiting cleanly:
   - `backend/app/main.py` — FastAPI app for `api`, with a `/healthz` route reading the heartbeat table (proves `api` can observe *all four* rows, since that's its eventual dashboard role) and a background task writing its own heartbeat.
   - `backend/app/engine/core.py` — `engine`'s loop.
   - `backend/app/feedd/core.py` — `feedd`'s loop.
   - `backend/app/worker/core.py` — `worker`'s loop.
4. `backend/app/cli/__init__.py` — `run_api`, `run_engine`, `run_feedd`, `run_worker` wrapper functions; `pyproject.toml` `[project.scripts]` wiring `api`, `engine`, `feedd`, `worker` to them.
5. `backend/app/cli/supervisor.py` — starts all four as subprocesses, restarts one that exits unexpectedly (not on a clean `stopped` shutdown it requested itself), terminates all four on its own shutdown; console-scripted as `supervisor`.
6. `backend/tests/integration/test_process_independence.py` — the literal proof: start `engine` and `api` as real subprocesses, confirm both heartbeat, kill `api` (`SIGTERM`/`taskkill`), confirm `engine`'s `last_heartbeat_at` keeps advancing with no gap larger than ~2 heartbeat intervals throughout, confirm `api`'s row shows `stopped`. A second test proves the supervisor restarts a forcibly-killed child. Both skip cleanly (named reason) when Postgres isn't reachable, matching F0.2's pattern.
7. Project-status update in `PROJECT_UPDATE.md` after implementation and after independent review.

## Acceptance scenarios

### A1 — Four independent entry points

- `uv run api`, `uv run engine`, `uv run feedd`, `uv run worker` each start, write an initial heartbeat row, and keep running until signaled.
- No process module imports another process's entry module (`app.engine.core` does not import `app.main`, etc.) — checked by a static import-boundary test, not just manual inspection.

### A2 — Kill/restart `api`; `engine` heartbeat and persisted state continue (the literal proof)

- With Postgres up: start `engine`, wait for 3+ heartbeats. Start `api`, wait for 3+ heartbeats. Kill `api` forcefully (not a graceful signal — proving `engine` doesn't even notice, let alone depend on, `api`'s presence). Wait 5 more seconds. `engine`'s `last_heartbeat_at` has advanced continuously with no gap; its `pid` and `started_at` are unchanged (same process, never restarted). `api`'s row is untouched at its last value (no new heartbeats after the kill) or marked `stopped` if it caught the signal.
- Restart `api`: a fresh process starts, gets a new `pid`, resumes heartbeating — proving restart doesn't require touching `engine`.

### A3 — Engine persists a state transition before acknowledging it

- Killing `engine` mid-loop (forcefully, no graceful shutdown chance) and querying its heartbeat row shows the last value it durably wrote, not a value that only ever existed in memory — there is no separate in-memory-only "current status" that could diverge from the row.

### A4 — Supervisor observes and restarts independently

- Start the supervisor; it launches all four. Forcefully kill one child's OS process. Within a bounded time, the supervisor starts a replacement (new `pid`, same `process_name`, heartbeating resumes). The other three children are never touched.
- Stopping the supervisor cleanly terminates all four children (no orphaned processes left heartbeating after the test).

## Verification

- All commands/scenarios in A1–A4, exact output in the completion report.
- `uv run ruff check .`, `uv run mypy backend --strict`, `uv run pytest` (full suite, Postgres both up and down).
- `uv run alembic -c backend/alembic.ini upgrade head` creates `process_heartbeat`; downgrade removes it cleanly.
- `git diff --check`, secret scan, local Markdown link resolution.
- Confirm `build/validate_manifest.py` and `build/validate_fixtures.py` are unaffected.

## Non-goals

- No Dhan connection, no strategy execution, no real jobs, no REST routers beyond `/healthz` — those are later features.
- No production/Linux supervision (systemd, containers) — Epic 13.
- No settings module / secret redaction — F0.4.
- No protected-path code (`engine/risk.py`, `engine/broker.py` do not exist yet; nothing here is on the protected list).

## Migration and rollback

First real product schema (`process_heartbeat`); fully reversible via `alembic downgrade`. No market/warehouse data. Revert the F0.3 commit(s) and run `alembic downgrade -1` to roll back before F0.4 depends on these process skeletons.
