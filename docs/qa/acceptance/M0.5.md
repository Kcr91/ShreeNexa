# M0.5 Acceptance Contract — Feature Manifest and Validated State Helper

## Feature

Convert the 102 product features from `SHREENEXA_CODEX_VSCODE_BUILD_PLAN.md` §6, plus the six M0 bootstrap tasks, into a single machine-readable `build/manifest.yaml`. Add a validator that checks manifest schema, dependency existence, cycle-freedom, and a generated (not handwritten) feature count. Introduce the validated `build/state.json` update helper referenced by `PROJECT_UPDATE.md` and by build plan §10.

## Required deliverables

1. `build/manifest.yaml` — one entry per M0.1–M0.6 and F0.1–F13.5, each with `id`, `name`, `depends_on`, `proof`, and `model`, transcribed from the approved build plan without silent correction.
2. `build/validate_manifest.py` — loads the manifest, validates required fields and ID format, confirms every `depends_on` reference resolves to a declared ID, performs a topological sort to prove the dependency graph is acyclic, and generates feature counts (total, M0 tasks, product features) rather than hardcoding them.
3. `build/tests/test_manifest.py` — pytest coverage for the validator: a valid manifest passes; a manifest with an unknown dependency reference fails; a manifest with an introduced cycle fails; the generated product-feature count equals 102 for the approved manifest.
4. `build/state_schema.py` (or equivalent) plus `build/update_state.py` — a small validated helper that reads/writes `build/state.json` against the field set in build plan §10 (`feature`, `status` enum, `branch`, `commit`, `tests`, `started_at`, `finished_at`, `blockers`), rejecting an invalid status value or a malformed call rather than writing a corrupt file.
5. `build/state.json` — initialized to reflect the true current status (M0.5, in progress) through the new helper, not hand-edited.
6. Project-status update in `PROJECT_UPDATE.md` after implementation and after independent review.

## Acceptance scenarios

### A1 — Manifest completeness and fidelity

- Every ID `M0.1`–`M0.6` and `F0.1`–`F13.5` named in the build plan appears exactly once.
- `name`, `depends_on`, `proof`, and `model` match the build plan's stated work unit, dependency cell, minimum-proof cell, and model code respectively. Dependency ranges (e.g. `F0.5–F0.7`) expand to the explicit member IDs.
- Any transcription ambiguity discovered in the source build plan is preserved literally and flagged in a `notes` field plus the completion report — it is not silently resolved.

### A2 — Schema and reference validation

- The validator rejects a manifest entry missing `id`, `name`, `depends_on`, `proof`, or `model`.
- The validator rejects a `depends_on` entry that does not match a declared `id`.
- ID values match `^(M0\.[1-6]|F(0|1[0-3]?|[1-9])\.\d+)$` (M0 bootstrap tasks or epic-scoped product features).

### A3 — Cycle-freedom

- A topological sort over the declared manifest completes without error.
- A deliberately introduced cycle (fixture manifest, not the real one) is rejected by the same code path, proving the check is real rather than vacuous.

### A4 — Generated count

- The validator reports total item count, M0 task count, and product feature count as computed values.
- For the approved manifest, the generated product feature count equals 102 (matching build plan §6/§7, "the manifest counts 102 product features"), and this equality is asserted by a test rather than typed into the manifest as a field.

### A5 — Validated state helper

- `build/update_state.py` rejects a `status` value outside `pending | in_progress | review | done | blocked | parked`.
- A successful update produces a `build/state.json` matching the §10 field set exactly, with no conversational history embedded.
- `build/state.json` is not edited directly during this feature; every write goes through the helper.

## Verification

- `python build/validate_manifest.py build/manifest.yaml` exits 0 and prints the generated counts.
- `python -m pytest build/tests/test_manifest.py -q`.
- Parse `build/manifest.yaml` and `build/state.json` and confirm both are valid YAML/JSON respectively.
- Resolve local Markdown links, scan changed files for secret-shaped content, and run `git diff --check`.
- Confirm no product code, backend/frontend scaffolding, or dependency lockfile was introduced.

## Non-goals

- No feature implementation work (F0.1 onward) begins here.
- No CI wiring — `build/validate_manifest.py` is run manually until F0.1 establishes the CI skeleton.
- No change to `AGENTS.md`, `.codex/config.toml`, or protected-path policy.
- No retroactive correction of the approved build plan's prose; discovered inconsistencies are reported, not rewritten.

## Migration and rollback

New files only; no schema or runtime-data impact. Revert the M0.5 commit(s) to roll back before M0.6 depends on the manifest.
