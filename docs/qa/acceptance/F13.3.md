# F13.3 Acceptance Contract: Single-User Password + TOTP Auth, Secure Sessions, Recovery Process, Rate Limiting, and Audit

## Feature Definition
- **Feature ID**: F13.3
- **Name**: Single-user password + TOTP auth, secure sessions, recovery process, rate limiting, and audit.
- **Dependencies**: F4.1, F13.2
- **Proof Requirement**: Security tests for session fixation, CSRF, brute force, secret storage, and WebSocket authorization.

## Invariants & Acceptance Criteria

1. **Single-User Password + TOTP 2FA (`backend/app/auth/`)**:
   - Master trader password hashed via PBKDF2-HMAC-SHA256 with 600,000 iterations and cryptographically random salt. Plaintext passwords are never stored or logged.
   - RFC 6238 Time-based One-Time Password (TOTP) standard implementation using HMAC-SHA1 over 30-second time steps.
   - 2-Step Login Sequence:
     - `POST /api/v1/auth/login`: verifies password, produces time-limited challenge token (`requires_totp: true`).
     - `POST /api/v1/auth/totp/verify`: validates challenge token + 6-digit TOTP code (with ±1 step clock skew tolerance).
     - On success: issues authenticated session cookie (`HttpOnly`, `SameSite=Strict`, `Path=/`) and anti-CSRF token.

2. **Account Recovery Mechanism**:
   - `POST /api/v1/auth/recovery`:
     - Allows emergency login when TOTP authenticator device is lost.
     - Requires master password + single-use emergency recovery code.
     - Recovery codes are stored strictly as SHA-256 digests and marked consumed upon use (cannot be replayed).

3. **Brute Force & Rate Limiting Defense**:
   - Sliding-window rate limiter per client IP:
     - Maximum 5 failed authentication attempts within 15 minutes.
     - Exceeding limit locks out the IP, returning HTTP 429 Too Many Requests with `Retry-After`.
     - Successful authentication resets failed attempt counter.

4. **Session Fixation & CSRF Protection**:
   - **Session Fixation**: When a user authenticates, any existing session is destroyed and a brand new cryptographically random 256-bit session identifier is generated.
   - **CSRF Protection**: Double-submit anti-CSRF token verification (`X-CSRF-Token` header) enforced on all state-mutating requests (`POST`, `PUT`, `DELETE`, `PATCH`). Missing or mismatched CSRF tokens are rejected with HTTP 403 Forbidden.

5. **WebSocket Authorization Invariant**:
   - Connecting to WebSocket endpoints (`/ws`, `/api/v1/ws`) requires an active, validated session.
   - Unauthenticated or expired WebSocket connections are immediately rejected with close code 4001 or HTTP 401.

6. **Immutable Audit Logging**:
   - All authentication events (`LOGIN_SUCCESS`, `LOGIN_FAILED`, `TOTP_VERIFY_FAILED`, `RECOVERY_USED`, `RATE_LIMITED`, `LOGOUT`) are recorded with timestamp, event type, client IP, and user-agent.
   - Secrets, passwords, TOTP codes, and recovery codes are strictly redacted and never recorded in logs.

7. **Verification & Proof Suite (`backend/tests/unit/test_auth_security.py`)**:
   - Session fixation proof: verifies session ID changes upon login; old session cannot access protected endpoints.
   - CSRF proof: mutating requests without `X-CSRF-Token` or with invalid token fail with HTTP 403.
   - Brute force proof: 5 consecutive invalid attempts trigger lockout / HTTP 429.
   - Secret storage proof: password hashes use PBKDF2 with >=600,000 rounds; recovery codes stored as hashes.
   - WebSocket authorization proof: validates connection rejection on invalid or missing session.
