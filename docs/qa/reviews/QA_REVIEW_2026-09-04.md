## 4. New findings from Epic 12

### QA-15 — Order ticket API fabricates paper fills server-side and never calls the paper broker
**Severity: CRITICAL** · Area: Backend / API · Feature: F12.3

[app/api/orders.py:196-205](../../../backend/app/api/orders.py#L196-L205):

```python
    # Paper mode execution
    simulated_order_id = f"ORD-PAPER-{req.security_id}-{req.quantity}"
    return TicketPlaceOrderResponse(
        success=True,
        mode=req.mode,
        order_id=simulated_order_id,
        correlation_id=correlation_id,
        order_status=OrderStatus.PENDING,
        message=f"Paper order {simulated_order_id} placed successfully.",
    )
```

The endpoint never imports or calls `paper_broker`. It builds an order ID from a string template and returns success. This is Revision 1's QA-04 relocated into the backend, where it is more dangerous: a client now receives an authoritative-looking server response confirming an order that no broker, engine, or ledger has ever seen.

The ID is also **deterministic**, not unique: two identical orders (same `security_id`, same `quantity`) produce the same `order_id`. Any downstream keying on order ID will silently collapse distinct orders into one.

A working paper path exists — `app/api/paper.py:118` calls `paper_broker.submit_orders([order])` — and F9.1's `PaperBroker` has persisted orders, fills and restart recovery. The ticket endpoint bypasses all of it.

**Fix:** delegate to `paper_broker.submit_orders()` and return the broker-assigned ID and status. Remove the string-template ID entirely. Add a test asserting the endpoint's returned order ID is retrievable via `GET /api/v1/paper/orders`.

### QA-16 — The F12.6 audit ledger is never called by any production code path
**Severity: CRITICAL** · Area: Backend / audit · Feature: F12.6

`app/engine/audit.py` (203 lines) implements a SHA-256 hash-chained, tamper-evident ledger with secret redaction and correlation-ID reconstruction. The implementation is sound. It has exactly one importer in the entire repository:

```
$ grep -rn "from app.engine.audit" backend/ --include=*.py
backend/tests/unit/test_audit_ledger.py:5:from app.engine.audit import AuditEvent, AuditEventType, AuditLedger
```

`broker.py`, `risk.py`, `api/orders.py`, `order_reconciler.py` and `continuous_recon.py` contain **no reference to the audit ledger at all**. No signal, risk decision, order request, order response, order update, reconciliation event, operator override or kill-switch activation is ever recorded.

F12.6's proof requirement is *"one trade can be reconstructed end to end; sensitive values are redacted; audit tampering is detectable."* Tampering detection is genuinely proven by `test_audit_ledger.py`. End-to-end reconstruction is proven only against events the test itself appends by hand. In the running system there is nothing to reconstruct, and F12.6 was recorded complete on that basis.

This also means the build plan's live-activation prerequisite of a complete audit trail cannot be satisfied by the current code, regardless of how the other gates land.

**Fix:**
- Instantiate a process-scoped `AuditLedger` and record at each boundary: signal generation, `RiskEngine.filter_order` outcome (both pass and reject), `DhanBroker.place_order` request and response, every `OrderReconciler` update, every `ContinuousReconciler` mismatch and freeze, and every `halt()`/`unhalt()`.
- Persist the chain (Postgres append-only table or an fsync'd log) — an in-memory ledger cannot satisfy "immutable" or survive the restart that reconciliation exists to handle.
- Add an integration test that places one order end to end and asserts the ledger contains a complete, verifying chain for that `correlation_id`.

### QA-17 — The F12.4 risk layer has no production callers, and its stated invariant is false
**Severity: CRITICAL** · Area: Backend / risk · Feature: F12.4

`app/engine/risk.py` opens by declaring:

```python
CRITICAL INVARIANTS:
1. No execution path reaches DhanBroker without passing pre-trade risk checks.
```

That invariant does not hold, and nothing enforces it. `RiskEngine` and `RiskFilteredBroker` have no production importer:

```
$ grep -rn "from app.engine.risk" backend/ --include=*.py
backend/tests/unit/test_continuous_recon.py:22:...
backend/tests/unit/test_risk_engine.py:17:...
```

Meanwhile the **only** production instantiation of `DhanBroker` in the entire application bypasses the risk layer completely — [api/orders.py:184](../../../backend/app/api/orders.py#L184):

```python
broker = DhanBroker(enable_live_trading=False)  # Default disabled
```

`DhanBroker` is an ordinary public class with a public constructor. Any module can instantiate it and call `place_order` directly, and the one module that does, does. There is no import guard, no private constructor, no module-level architecture test.

F12.4's proof requirement is *"Exhaustive test proves no path reaches `DhanBroker` without risk filtering."* The suite contains one positive test, `test_broker_path_enforcement_via_risk_filtered_broker`, which confirms that orders routed *through* `RiskFilteredBroker` are filtered. It does not enumerate paths, and it would pass unchanged if every caller bypassed the wrapper — which is the actual state of the code.

Two lesser issues in the same module: `RiskEngine` state (`_is_halted`, `_daily_realized_loss`, `_order_timestamps`) is per-instance and in-memory, so a kill switch does not survive an API or engine restart and is not shared across processes — the `api` and `engine` processes would each hold their own independent halt state. And `record_loss` only accumulates realised loss passed in by a caller; with no caller, `max_daily_loss` can never trigger.

**Fix:**
- Make `DhanBroker` unreachable except through `RiskFilteredBroker`: move it to a private module, or have its constructor require a risk-engine token that only `RiskFilteredBroker` can mint.
- Replace the single positive test with an **architecture test** that walks the AST of `backend/app/**` and fails on any `DhanBroker(` construction or `.place_order(` call outside `risk.py`. That is what "exhaustive" requires.
- Route `api/orders.py` through `RiskFilteredBroker`.
- Move halt state and the daily-loss tally into Redis so the kill switch is process-wide and restart-durable.

### QA-18 — The uncertain-order retry guard is never armed and does not survive restart
**Severity: HIGH** · Area: Backend / API · Feature: F12.1, F12.3

[api/orders.py:26](../../../backend/app/api/orders.py#L26) declares `_uncertain_orders: dict[str, str] = {}`. It is **read** at line 166 (blocking retry) and line 209 (status reporting), but **never written** anywhere in production code. The only writes in the repository are in the test file:

```
backend/tests/unit/test_order_ticket_api.py:146:    _uncertain_orders[corr_id] = "ORD-UNCERTAIN-123"
backend/tests/unit/test_order_ticket_api.py:178:    _uncertain_orders["CORR-TEST"] = "ORD-UNCERTAIN-999"
```

So in the running system the dict is permanently empty: `/place` never blocks a retry and `/status` always reports `retry_allowed: true`. The mechanism cannot arm itself because `place_ticket_order` never calls the broker, so it never observes a `DhanTimeoutError` or a `PENDING_BROKER_CONFIRMATION` response.

Even once armed, module-level dict state is lost on every API restart — and an API restart is precisely the scenario in which an operator, having seen a timeout, is most likely to retry. F12.3's proof *"uncertain order state blocks blind retry"* is verified only against manually injected state.

**Fix:** populate the guard from the broker's actual `PENDING_BROKER_CONFIRMATION` responses and from `DhanTimeoutError`; persist it in Redis or Postgres keyed by correlation ID; clear it only after `get_order_by_correlation_id` confirms broker truth. Add a test that drives a transport timeout through the endpoint and asserts the second identical request returns 409.

### QA-19 — F12.2 delivers frame parsing but no WebSocket client
**Severity: HIGH** · Area: Backend / live order updates · Feature: F12.2

`app/dhan/order_stream.py` correctly models the Dhan order-update payloads and builds the MsgCode 42 authorisation handshake for `wss://api-order-update.dhan.co`. But its public surface is entirely synchronous frame handling:

```
build_order_stream_auth_message()   DhanOrderUpdateEvent.from_raw_json()
handle_raw_frame()                  handle_postback()                dispatch()
```

There is no connection, no `async`, no reconnect state machine, no heartbeat, and no sequence-gap detection. Nothing ever opens the socket — the module has no production importer, so `handle_raw_frame` is never fed a frame by anything but a test.

F12.2's scope was *"Live Order Update WebSocket, postback ingestion, deduplication, sequence gaps, and reconciliation"* with the proof *"duplicate/lost/out-of-order events converge to broker truth without duplicate fills."* Deduplication and convergence are implemented in `order_reconciler.py` and tested against synthetic event lists — which is worthwhile — but the transport that would deliver those events does not exist. This is the same gap as QA-05 (the browser fan-out), now repeated for the broker-side stream.

**Fix:** implement the async client with connect, MsgCode 42 handshake, heartbeat, exponential reconnect and resubscribe, feeding `handle_raw_frame` into `OrderReconciler`. Run it under the `engine` or `feedd` process. Add an integration test driving a fake WebSocket server through disconnect and replay.

### QA-20 — The LIVE branch of the order ticket is unreachable scaffolding
**Severity: HIGH** · Area: Backend / API · Feature: F12.3

[api/orders.py:182-193](../../../backend/app/api/orders.py#L182-L193):

```python
        broker = DhanBroker(enable_live_trading=False)  # Default disabled
        try:
            # If broker live trading is disabled, this raises LiveTradingDisabledError
            _ = broker
            raise LiveTradingDisabledError(
                "Live trading is disabled. Explicit operator approval is required."
            )
        except LiveTradingDisabledError as exc:
            raise HTTPException(status_code=403, detail=str(exc)) from exc
```

Three problems. The constructor hardcodes `enable_live_trading=False`, so `SHREENEXA_ENABLE_LIVE_TRADING=true` has no effect on this path. The `try` block raises the exception it then catches — `_ = broker` is a no-op standing in for a call that was never written, and `broker.place_order` is never invoked. And because the branch always returns 403, none of F12.4 (risk), F12.5 (reconciliation) or F12.6 (audit) is reachable from the API at all.

Being closed-by-default is the right posture, and the endpoint failing safe is not itself a defect. The defect is that this is written to look like an implemented, gated live path — the comment asserts behaviour the code does not have — so the F12.3 acceptance evidence describes a live ticket that was never built. A reader, or a future change flipping the flag, would reasonably assume the wiring exists behind the gate.

**Fix:** either implement the path properly — construct through `RiskFilteredBroker`, let `DhanBroker` read the env flag, call `place_order`, and let `LiveTradingDisabledError` and `StaticIPMismatchError` propagate as 403 — or delete the branch and return 501 with an explicit "live ticket not implemented" message. Update `docs/qa/acceptance/F12.3.md` to state which.

### QA-21 — Charges and margin estimator forks the cost model with hardcoded rates
**Severity: MEDIUM** · Area: Backend / API · Feature: F12.3, F3.3, F8.6

`estimate_order_charges` ([api/orders.py:92-160](../../../backend/app/api/orders.py#L92-L160)) computes brokerage, STT/CTT, exchange charges, SEBI fees, stamp duty and GST from literals embedded in the route handler — `0.001`, `0.00025`, `0.0005`, `0.0000297`, `0.000001`, `0.00015`, `0.18`.

F3.3 already delivers an *"effective-dated Indian cost model"* at `app/engine/costs.py`, reconciled against a redacted real Dhan contract note. F9.4's binding requirement was that forward-test results reuse the Epic 3 metric registry *"without calculation forks"*. This is a fork: the same statutory rates now exist in two places, one of them not effective-dated, so a rate change (a Union Budget STT revision, say) will update backtest costs and leave the order ticket quoting stale figures — with no test comparing the two.

The margin figure is worse. `required_margin = turnover * 0.20 + total_charges` with the comment `# Approx 5x MIS leverage` is an invented heuristic presented to the trader as an estimate. F8.6 built a Dhan margin adapter against `/v2/margincalculator/multi` at `app/dhan/margin_adapter.py`, and its proof required that *"unavailable margin is explicit, never zero"* — the spirit of which a fabricated 20 % plainly violates. Real intraday leverage is instrument- and broker-specific and does not resemble a flat 20 % across segments.

**Fix:** delegate charges to `app/engine/costs.py` with the order's trade date; delegate margin to the F8.6 adapter, surfacing "margin unavailable" when the broker call fails rather than substituting a heuristic. Add a parity test asserting the ticket estimate and the backtest cost model agree on a shared fixture.

## 8. Recommendation

**Do not mark Epic 12 complete, and do not proceed to live activation.**

The distinction that matters here is between *delivered* and *in force*. F12.4's kill switch, F12.5's freeze-on-mismatch and F12.6's audit trail are the three controls the live-activation checklist depends on, and all three are currently unreachable code. A kill switch nothing can call does not halt trading; an audit ledger nothing writes to cannot reconstruct a trade; a reconciler with no event source cannot detect a mismatch. Their unit tests pass, which is why the gates are green — but the gates were never designed to catch this, and Revision 1 flagged the same pattern in Epics 4, 7 and 11 before Epic 12 repeated it.

The most valuable single change is not any individual fix: it is **adding integration-level gates that fail when a module has no production caller.** An architecture test asserting that every module under `app/engine/` is imported by something under `app/api/` or `app/worker/`, and the AST test in QA-17, would have caught QA-16, QA-17 and QA-19 at commit time.
