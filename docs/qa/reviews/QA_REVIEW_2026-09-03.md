## 1. Executive summary

Automated gates are green. Product-level integration is not.

| Gate | Result |
|---|---|
| `ruff check .` | **PASS** — all checks passed |
| `mypy` (strict, 195 files) | **PASS** — no issues |
| `pytest backend/tests` | **FAIL** — 563 passed, **1 failed**, 30 skipped |
| `vitest run` (frontend) | **PASS** — 57 files, 185 tests |
| `tsc --noEmit` | **PASS** |
| `vite build` (production) | **PASS** — 402.71 kB bundle |

The single test failure is not cosmetic: it was **caused by adding your live token to `.env`**, and it exposes a credential-precedence and test-hermeticity defect (QA-01).

The dominant theme across the review is that **the backend and frontend were each built and tested in isolation and were never wired to each other.** Epics 0–11 and 13 are recorded complete with passing unit tests, but at the seam:

- No API route enforces authentication, and the frontend auth is a hardcoded always-logged-in stub (QA-02, QA-03).
- The browser WebSocket fan-out (F7.4) is a library class that is never mounted as an endpoint (QA-05).
- The order ticket reports "order submitted successfully" without making any network call at all (QA-04).
- Two dashboard widgets render `Math.random()` data, one of which fabricates the `securityId` field used to identify instruments for orders (QA-06).
- The token-health badge can never show a healthy state because backend and frontend disagree on the status vocabulary, and it cannot reach the backend anyway (QA-07, QA-08).

For F12.1 specifically, the safety gates (disabled-by-default, IP preflight, no-blind-retry) are correctly implemented and tested, but the static-IP check trusts a self-declared environment variable rather than the real egress IP (QA-09), and the slicing logic the acceptance contract demands is dead code (QA-11).

**Verdict:** Not eligible for live activation. Not currently deployable as a multi-process product. Blocking issues: QA-01 through QA-06.

### QA-01 — Test suite reads the developer's real `.env`; `.env` silently overrides the encrypted DPAPI store
**Severity: CRITICAL** · Area: Backend / config · Feature: F0.4

**Evidence:** `pytest` failure introduced by your credential update:

```
backend/tests/unit/test_dhan_token_cli.py::test_cli_set_status_clear_round_trip
AssertionError: assert 'source     : dpapi' in 'status: valid\nsource: environment\n...'
```

The test calls `monkeypatch.delenv("DHAN_ACCESS_TOKEN")`, but `Settings.load()` ([backend/app/config.py:76-90](backend/app/config.py#L76-L90)) reads `.env` from disk via `dotenv_values` **in addition to** `os.environ`. `delenv` cannot unset a value that comes from a file, so the resolver still finds your live token and reports `source=environment`.

Two distinct defects:

1. **Non-hermetic tests.** Test outcomes now depend on the contents of an untracked local file. The suite was green only because `.env` was previously blank. This directly undermines the F12.1 proof *"no test can reach live Dhan"* — that guarantee currently rests on tests not happening to construct an HTTP transport, not on credentials being unavailable.
2. **Precedence inversion.** `resolve_dhan_credentials` ([backend/app/dhan/credentials.py:130-145](backend/app/dhan/credentials.py#L130-L145)) tries environment first, DPAPI second. Because `.env` is folded into "environment", a plaintext token on disk **silently shadows** the encrypted DPAPI store that `.env.example` explicitly recommends (`python -m app.dhan.token set`). The documented secure path is defeated the moment `.env` is populated, with no warning.

**Fix:**
- Add an autouse session fixture in `backend/tests/conftest.py` that forces hermetic settings — e.g. `monkeypatch.setattr(app.config, "get_settings", lambda: Settings(...))`, or set `SHREENEXA_ENV_FILE=""` and have `Settings.load()` honour it. Tests must never read the repo `.env`.
- Separate the two sources in `Settings`: keep dotenv values in a distinct field so `resolve_dhan_credentials` can order them **OS env > DPAPI > .env file**, matching the documented security posture.
- Emit a startup `WARNING` when a token is resolved from a plaintext `.env` while a DPAPI store also exists.
- Add a regression test asserting DPAPI wins over a populated `.env` file.

### QA-02 — No API route requires authentication
**Severity: CRITICAL** · Area: Backend / security · Feature: F13.3, F7.4

**Evidence:** `app/api/auth.py` implements password + TOTP, session cookies (`httponly`, `samesite=strict`, `secure` in prod) and CSRF tokens. **No other router consumes it.** Grep of `Depends` across all 22 routers:

```
ai.py:0  backtests.py:0  calibration.py:0  depth.py:0  feature_builder.py:0
indicators.py:0  investing.py:0  margin.py:0  monitoring.py:0  options.py:0
options_analytics.py:0  paper.py:0  screeners.py:0  strategy_builder.py:0
strategy_ir.py:0  watchlists.py:0  ws.py:0
```

The four non-zero files (`feed`, `heatmap`, `instruments`, `universe`) use `Depends` for dependency injection (`get_db_engine`, `get_budget_manager`), **not** for auth. There is no auth middleware in [backend/app/main.py:89-111](backend/app/main.py#L89-L111).

Anyone who can reach the API port has full unauthenticated access to paper order placement (`POST /api/v1/paper/orders`), the AI strategy generator, holdings and investing data, monitoring, and — most seriously — the **feature-builder router**, which drives the Codex task runner (F11.3). No CSRF validation is performed anywhere, despite tokens being issued.

This directly contradicts the F13.3 proof requirement *"security tests for session fixation, CSRF, brute force, secret storage, and WebSocket authorization."* The service-level tests exist; the enforcement does not.

**Fix:**
- Add `app/api/deps.py` with `require_session(shreenexa_session: str = Cookie(None)) -> SessionInfo` raising `401`, plus `require_csrf(x_csrf_token: str = Header(None))` for all non-GET methods.
- Apply at router construction so it cannot be forgotten per-endpoint: `app.include_router(paper_router, dependencies=[Depends(require_session)])`.
- Maintain an explicit allowlist of unauthenticated paths (`/healthz`, `/api/v1/auth/login`, `/api/v1/auth/totp/verify`) and add an architecture test that fails if any router outside the allowlist is mounted without `require_session`.
- Move sessions out of the in-memory `dict` in `auth/service.py:54` into Redis — they are currently lost on every API restart and are not shared across workers, so any multi-worker or restarted deployment logs the user out and cannot revoke sessions reliably.

### QA-04 — Order ticket fabricates a successful order confirmation without any network call
**Severity: CRITICAL** · Area: Frontend / dashboard · Feature: F9.2, F12.3

**Evidence:** [frontend/src/order/execution.ts:97-124](frontend/src/order/execution.ts#L97-L124):

```ts
const orderId = `ORD-${Date.now()}-${Math.random().toString(36).substring(2, 6).toUpperCase()}`;
return {
  success: true,
  orderId,
  executionMode,
  message: `${executionMode} order ${orderId} submitted successfully to SimBroker engine.`,
};
```

`placeOrder` performs validation and then **returns a fabricated success with an invented order ID.** There is no `fetch`, no API client call, no engine dispatch. The message explicitly claims submission "to SimBroker engine" — an engine that never received it.

The trader sees a green confirmation and an order ID that exists nowhere in the system. Meanwhile a *real* paper path exists and works: `PaperTradingWidget` correctly calls `POST /api/v1/paper/orders` ([PaperTradingWidget.tsx:261-295](frontend/src/widgets/builtin/PaperTradingWidget.tsx#L261-L295)). The order ticket simply does not use it.

Compounding issues in the same widget ([OrderTicketWidget.tsx:59](frontend/src/widgets/builtin/OrderTicketWidget.tsx#L59)):

- `const availableFunds = 500000; // Mock development buying power` — the "insufficient funds" validation is checked against a fake balance, not `GET /v2/fundlimit`.
- Margin is computed client-side by `calculateStockMargin` rather than via the F8.6 Dhan margin adapter (`/v2/margincalculator/multi`), which already exists at `app/dhan/margin_adapter.py`. F8.6's proof required *"unavailable margin is explicit, never zero"*; a locally-invented number is worse than unavailable.
- `ProductType = "CNC" | "MIS" | "NRML"` ([order/types.ts:4](frontend/src/order/types.ts#L4)) does not match the DhanHQ v2.5 enum `CNC | INTRADAY | MARGIN | MTF` (`dhan-api-docs.md:3733`). `MIS` and `NRML` are Zerodha vocabulary and will be rejected by Dhan.

**Fix:**
- Make `placeOrder` async and POST to `/api/v1/paper/orders`, returning the **broker-assigned** order ID. Never synthesize an order ID client-side.
- On any non-2xx or network error, surface a failure state; on timeout show "status unknown — do not retry" (mirroring the backend `PENDING_BROKER_CONFIRMATION` invariant), never a success.
- Replace `availableFunds` with a fetch of live fund limits; if unavailable, disable submission and say so.
- Replace client-side margin with the F8.6 adapter; render "margin unavailable" when the broker call fails.
- Align `ProductType` to the Dhan enum, and generate shared types from the backend Pydantic models to stop this class of drift.

### QA-06 — Dashboard widgets render fabricated market data, including a random `securityId`
**Severity: CRITICAL** · Area: Frontend / dashboard · Feature: F4.4, F7.5

**Evidence:** The build plan's binding rule for F4.4 is explicit: *"Widgets not yet implemented use honest 'not available yet' placeholders, **never fake data**."* Two widgets violate this.

**`WatchlistWidget`** ([WatchlistWidget.tsx:82-88](frontend/src/widgets/builtin/WatchlistWidget.tsx#L82-L88)) — when a user adds a symbol:

```ts
securityId: Math.floor(1000 + Math.random() * 90000).toString(),
ltp: Math.floor(100 + Math.random() * 3000),
changePct: Number((Math.random() * 4 - 2).toFixed(2)),
volume: Math.floor(100000 + Math.random() * 5000000),
```

This is the most dangerous single line in the frontend. `securityId` is **the field DhanHQ uses to identify the instrument to trade** (`dhan-api-docs.md:3737` — *"securityId | string | Yes | Exchange standard ID for each scrip"*). A randomly generated value is not a placeholder; it is a valid-looking identifier for an arbitrary, unrelated instrument. The moment any order path reads `securityId` from a watchlist entry — the natural next step for F12.3 — this becomes a wrong-instrument order. It also persists to storage, so the fabricated value survives reloads and looks authoritative.

The F7.5 proof required *"symbols survive instrument-master refresh"*. These symbols were never resolved against the F0.7 instrument master (`app/dhan/instruments.py`, 570 lines, fully implemented and exposed via `/api/v1/instruments`).

**`ChartWidget`** ([ChartWidget.tsx:6-40](frontend/src/widgets/builtin/ChartWidget.tsx#L6-L40)) — `generateMockBars()` produces random-walk OHLCV for RELIANCE/TCS on hardcoded January 2026 dates, rendered with no "sample data" label. F4.5 built a UDF-shaped datafeed adapter over the warehouse; the chart does not use it. Indicators (SMA 20, RSI 14) are then computed over this noise and displayed as analysis.

**Fix (priority order):**
1. **Immediately** stop generating `securityId`. Resolve symbols through `GET /api/v1/instruments/search`; if resolution fails, refuse to add the symbol with a visible error. Never persist an unresolved instrument.
2. Purge existing persisted watchlists containing fabricated IDs — add a migration that drops entries whose `securityId` cannot be re-resolved against the instrument master.
3. Point `ChartWidget` at the F4.5 datafeed adapter. If no data is returned, render the empty/boundary state F4.6 already specifies.
4. Delete `generateMockBars` and the random fields from production code; move any needed fixtures into `*.test.tsx`.
5. Add a lint rule (`no-restricted-syntax` on `Math.random`) for `frontend/src/widgets/builtin/**` excluding tests, so this cannot regress.

### QA-07 — Token-health badge can never show a healthy state (backend/frontend contract mismatch)
**Severity: HIGH** · Area: Frontend / backend contract · Feature: F0.4

**Evidence:** Backend `TokenStatus` ([backend/app/dhan/health.py:14](backend/app/dhan/health.py#L14)):

```python
TokenStatus = Literal["valid", "expiring_soon", "expired", "unknown_expiry", "missing", "revoked"]
```

Frontend `TokenHealthResponse` ([frontend/src/api/client.ts:23](frontend/src/api/client.ts#L23)):

Only two of six values overlap. Verified against your live credentials, the backend returns:

- Generate the TypeScript types from the FastAPI OpenAPI schema (`openapi-typescript`) in a build step so this drift is caught at `tsc` time rather than silently in production.

### QA-08 — API client hardcodes `http://127.0.0.1:8000`, bypassing the dev proxy and breaking production
**Severity: HIGH** · Area: Frontend / deployment · Feature: F4.1, F13.2

**Evidence:** [frontend/src/api/client.ts:36](frontend/src/api/client.ts#L36):

```ts
constructor(baseUrl: string = "http://127.0.0.1:8000") {
```

`vite.config.ts` correctly proxies `/api` → `http://127.0.0.1:8000`, and every widget uses relative paths (`fetch("/api/v1/depth/watchlist")`) which work. The shared `ApiClient` does not — it issues **absolute cross-origin** requests to port 8000, and `main.py` registers **no `CORSMiddleware`**. The browser blocks the request.

`Header.tsx` then swallows it:

```ts
.catch(() => { setTokenHealth({ status: "not_configured", message: "Offline / Dev Stub" }); });
```

So the token banner shows a plausible-looking "Offline / Dev Stub" that is actually a CORS failure — masking QA-07 and making the banner permanently non-functional in the browser. (This is why the mismatch in QA-07 has gone unnoticed: the response never arrives to be mis-rendered.)

In production behind Caddy TLS (F13.2), `http://127.0.0.1:8000` refers to the **viewer's own machine** — a hard failure plus a mixed-content block on an HTTPS origin.

**Fix:**
- Default `baseUrl` to `import.meta.env.VITE_API_BASE_URL ?? ""` so requests are same-origin relative in both dev (proxied) and production (Caddy).
- Add `credentials: "include"` to the fetch options so session cookies are sent (required for QA-02/QA-03).
- Do not convert errors into a benign status. Distinguish network failure (show "API unreachable" in red) from `not_configured`.
- Derive the WebSocket URL the same way: `${location.protocol === "https:" ? "wss" : "ws"}://${location.host}/api/v1/feed/ws`.
- Keep `CORSMiddleware` out of production; if needed for dev, restrict it to `http://localhost:5173` with `allow_credentials=True`.

### QA-09 — Static-IP preflight trusts a self-declared env var, not the real egress IP
**Severity: HIGH** · Area: Backend / F12.1 safety · Feature: F12.1

**Evidence:** [backend/app/dhan/ip.py:18-25](backend/app/dhan/ip.py#L18-L25):

```python
def get_current_outbound_ip() -> str | None:
    for env_var in ("SHREENEXA_STATIC_IP", "OUTBOUND_STATIC_IP", "HOST_PUBLIC_IP"):
        val = os.environ.get(env_var)
        if val and val.strip():
            return val.strip()
    return None
```

The function never determines the host's actual outbound IP. It reads a value the operator typed, then compares it to Dhan's whitelist from `/v2/ip/getIP`. If someone sets `SHREENEXA_STATIC_IP` to the whitelisted Lightsail address while running from a laptop on a residential connection, **the preflight passes and orders are dispatched from a non-whitelisted IP**. They will be rejected by Dhan under SEBI rules, but the terminal's own safety gate contributed nothing — it verifies a configuration string against a configuration string.

The F12.1 acceptance contract (§2) requires validating that *"the host outbound public IP matches"*, and the build plan's live-activation checklist requires *"outbound host IP matches Dhan whitelisted Primary or Secondary."* Neither is actually verified.

The control is also entirely undocumented: `SHREENEXA_STATIC_IP` and `SHREENEXA_ENABLE_LIVE_TRADING` appear **nowhere** in `.env.example`, `infra/`, or `docs/runbooks/` — verified by grep. The two variables that gate real money are known only to whoever reads `ip.py` and `broker.py`.

**Fix:**
- Actually resolve egress IP at preflight: query a hardened IP echo service (or Dhan's own response metadata) with a short timeout, cached for the process lifetime. Treat a resolution failure as **fail-closed** (block the order) — which the current code already does correctly when the var is unset.
- Keep the env var only as an explicit, logged override for offline testing, named unambiguously (`SHREENEXA_STATIC_IP_OVERRIDE`), and refuse to honour it when `ENVIRONMENT=production`.
- Document both variables in `.env.example` and in a `docs/runbooks/live-activation.md` checklist.
- Add a test asserting that a mismatched *resolved* IP raises `StaticIPMismatchError` and that no order endpoint was called.

### QA-10 — Rate limiter enforces only the per-second window; per-minute/hour/day limits are unimplemented
**Severity: HIGH** · Area: Backend / Dhan compliance · Feature: F0.6, F1.2, F1.3

**Evidence:** `dhan-api-docs.md:476-485` documents multi-window limits:

| Window | Order APIs | Data APIs | Quote APIs | Non-Trading |
|---|---|---|---|---|
| per second | 10 | 5 | 1 | 20 |
| per minute | 250 | — | Unlimited | Unlimited |
| per hour | 1000 | — | Unlimited | Unlimited |
| per day | 7000 | 100000 | Unlimited | Unlimited |

`config/dhan_limits.yaml` and `limits_config.py` define **only `rate` and `burst`** — a single per-second token bucket per category. No minute, hour, or day window exists in `InMemoryTokenBucket` or the Redis Lua script.

Concrete consequences:

- Sustained order flow at the configured 10/s reaches 600/min — **2.4× the documented 250/min cap** — and 36,000/hour against a 1,000/hour cap. The limiter will drive the account into `DH-904` / `RL001` rate-limit rejections mid-strategy.
- Data APIs at 5/s exhaust the 7,000/day budget in roughly 23 minutes. The F1.2/F1.3 historical backfills are long-running and resumable by design; they will be throttled or blocked partway through with no local accounting to explain why.
- `dhan-api-docs.md` is internally inconsistent on daily caps (§476 says Orders 7,000/day and Data 100,000/day; §6358 says the reverse). This should be resolved with Dhan support and recorded — but either way, **neither is enforced**.

Also unenforced: *"Order Modifications are capped at 25 modifications/order"* (`dhan-api-docs.md:487`). There is no per-order modification counter anywhere.

Separately, `option_chain` is a **single global bucket**. The docs state the limit is 1 request per 3 s **per unique underlying/expiry**, and that different underlyings may be fetched concurrently (`dhan-api-docs.md:3237`). The current design serialises all option-chain traffic — safe, but it will make multi-underlying chain refresh (F8.3/F8.4) unusably slow at scale.

**Fix:**
- Extend `RateLimitSpec` to a list of windows: `[{per: 1s, limit: 10}, {per: 60s, limit: 250}, {per: 3600s, limit: 1000}, {per: 86400s, limit: 7000}]`. `acquire` must satisfy **all** windows.
- Implement day/hour windows as Redis fixed-window counters keyed by UTC date/hour with matching TTLs — these must survive process restarts, so the in-memory bucket alone is insufficient for the daily budget.
- Add a per-order modification counter enforcing the 25 cap before `modify_order` dispatches.
- Key the option-chain bucket per `underlying:expiry` rather than globally.
- Expose remaining daily budget through the F13.5 monitoring endpoints and alert at 80 %.
- Extend the existing Hypothesis concurrency test to assert no window is exceeded, not just the per-second one.

### QA-11 — F12.1 slicing logic is dead code; correlation IDs do not match the acceptance contract
**Severity: MEDIUM** · Area: Backend / F12.1 · Feature: F12.1

**Evidence:** Grep confirms `calculate_order_slices` and `EXCHANGE_FREEZE_LIMITS` ([orders.py:97-140](backend/app/dhan/orders.py#L97-L140)) are referenced **only by `test_dhan_orders.py`** — never by `DhanBroker` or `DhanRestClient`. `DhanBroker.place_sliced_order` forwards the full quantity to Dhan's server-side `/orders/slicing` endpoint and lets Dhan slice it.

Using the server-side endpoint is the correct choice. But the F12.1 acceptance contract (§3) states *"Slicing logic automatically partitions orders exceeding exchange freeze limits into sequential slices with **unique correlation IDs**"* — and 17 passing tests exercise a function that production never calls, which reads as verified coverage of a behaviour that does not exist. Only one correlation ID is generated for the whole sliced request.

Two further contract gaps:

- §3 requires correlation IDs of the form `NEXA-<strategy_id>-<timestamp>-<uuid4_prefix>`. `generate_correlation_id` ([orders.py:104-109](backend/app/dhan/orders.py#L104-L109)) produces `NX-<ts>-<8hex>` with **no strategy_id**. The contract's stated purpose — *"deterministically linked to trade intents"* — is not met, which will block F12.5 reconciliation and F12.6 audit reconstruction ("one trade can be reconstructed end to end").
- §3 lists `DhanSliceOrderResponse` as a deliverable. It does not exist; `place_sliced_order` returns `list[DhanOrderResponse]`.

`DEFAULT_FREEZE_LIMIT = 1800` is also applied to **every** instrument including equities, which have no such freeze quantity — if the helper were ever wired up it would wrongly slice a 5,000-share equity order.
